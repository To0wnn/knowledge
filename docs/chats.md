# Agents, chats and approvals

Moved from the README; [back to the README](../README.md). The web UI's attention board and the chats with agents on your own pcs, including how a tool call is approved
from a phone. The pc side runs in the companion ([companion.md](companion.md)).

## Agents

- **Agents (chat with your agents):** only for a person with at least one token whose "Agents (remote control)"
  switch is on ([companion.md](companion.md#agents-remote-control-per-token)). The web UI's **Agents** view (route `#/chats`, key `A`, the start page;
  `#/inbox` keeps working and opens the same view) is one list on the left with the open chat on the right, fed by the
  **attention board** (`GET /ui/api/board`); its sidebar badge counts what needs you, on every view and in every
  project. The header filters the list and Tasks to one project ("show all" says how many Needs-you items the filter
  hides) and shows when the fullest usage window resets. The list is grouped: **Needs you**, each row saying why (a
  chat whose agent answered and you have not opened since, a refused tool call or error in its last turn, an approval
  it asks, a failed worker of the last week with the companion's reason (`why`), a worker whose pc went offline ("pc
  offline since <time>", no Stop), a task line waiting for your approval, a task woken that nobody took, a result or
  hand-over to a person (`result`: read it, then remove the line; it never starts anything), a task whose "start
  after" task was cancelled (`blocked`)); **Review** (a branch with commits ready to merge: View diff, Merge, Reject; a finished worker with nothing to merge is under Done today); **Working** (chat
  turns, workers, task lines a session holds, and open task lines for an agent with a "Start on <pc>" button per pc
  that may take it); **Done today** (folded: chats read, workers ended, results handed back). A chat row shows its
  `outcome`, the last sentence the agent said (plain text, at most 160 characters). Quick actions on a row: Allow or
  Deny an approval, Merge or Reject a review, a one-line Reply; Snooze (1 h or until tomorrow), Dismiss and Archive sit in the row's ⋯ menu. Opening a
  chat marks it read (chats from before 0.17 count as read; a turn you stopped yourself and replies older than a week
  do not need you). Dismiss takes a Needs-you item off your own board until it changes; Snooze (`until`, Unix seconds,
  at most 30 days ahead) hides it until that time or until it changes, whichever comes first (stored per person on
  the server, `POST /ui/api/board/dismiss` with `{key, sig, until?}`). With Matrix configured
  (`KNOWLEDGE_MATRIX_URL/ROOM/TOKEN`), a new Needs-you item on an admin's board gives one Matrix message in that room,
  with a link to the item itself, `<KNOWLEDGE_PUBLIC_URL>/ui#/inbox/<key>` (every board item has a stable `key`): once
  per item and version (the key and signature Dismiss uses), at most `needs_per_hour` an hour (admin page, Settings;
  0 = off, default 6; more at once give one summary, the rest wait for room), and none while an admin has the board
  open (polled in the last 2 minutes: they see it there). A woken task nobody took keeps its own notice, now with the
  same link. Non-admins get none: the room is the admin's. A row opens its chat on the right (Esc or Back returns), a
  task its memo line, a worker how to look at it. On a phone the list is the start screen and a chat opens full
  screen. **Side by side** (`#/chats?view=board`, formerly "Board") shows several chats next to each other on a canvas you pan and zoom. **Grid** (`#/chats?view=grid`, a trial next to it) tiles the same cards to fill the screen: as many columns of at least 480 px as fit, balanced (4 chats 2×2), two rows on screen and the rest scrolls, per project the chat that last finished first (its turn, subagents and background shells all ended, not by your own Stop) or asked an approval; a new message, its events or reading it never move a card; no zoom, pan or dragging. Chat cards and workers
  carry a **git button** (`task/KN-12 · ●3 · ↑2↓0`: branch, changed files, commits ahead/behind `main`/`master`, or
  the upstream on main itself), which the companion counts once a round per folder with `GIT_OPTIONAL_LOCKS=0` and
  sends in its report (the linked folder only, `-- .`, also inside a bigger repo); a tap asks that pc for the diff (`POST /ui/api/git/diff`, handed to the companion with the chat
  messages, answered on `POST /machine/chats/diff`): the stat, untracked files by name and `git diff <merge-base>`,
  capped at 200 kB, shown as text. A running worker's card also gets its `progress` from the companion's report:
  newest commit subject, commits, changed files and the last 3 log lines (secrets masked on the pc and again on the
  server). A
  chat is a conversation with Claude Code, Codex or agy on one of your own pcs, in a folder linked to a project there,
  as in a terminal: the answer streams in (text, plus one line per tool call or refused call), the next message
  continues the same conversation, Stop ends a running turn and drops the waiting line. A message sent while the agent answers waits in line (up to 5 per chat, button "Queue") and goes in when the turn ends; with messages waiting and an empty box the button turns red "Force": the first waiting message goes into the running turn without stopping it (the server hands it to the companion once, `steer` in `GET /machine/chats`; the companion parks it in `companion/chats/<id>.steer`; the agent's PostToolUse hook `watch.py` gives it to the main agent after its next tool call, never to a subagent, which names an `agent_id`, nor to another session: the parked line carries the chat's session and the hook takes it only in that one, so a Codex/agy subagent or a CLI the chat started does not; a turn that is ending takes none and a new turn removes a left-over file; the server parks it only for a turn that runs); the turn's end reports `steered: delivered|pending`, and one not read in time goes in next; one on its way at a time; Stop drops it. Enter is a new line, Ctrl/Cmd+Enter presses the button; **+ New chat** opens a draft in the chat pane (`#/chats/new`, no dialog): an empty box, focused, and under it one model chip; the chat is made on the first message (`POST /ui/api/chats`, then the message with its model and effort). The folder is a linked folder of the sidebar's project on a pc that runs the chosen model (a list only when there is more than one; the pc follows from it); the last model, effort and folder are remembered in the browser. The chip ("Opus · high ▾") opens one panel: the models grouped by family (Claude, GPT, Gemini, other; each agent's own models first, the agent named small under each), "<agent>'s own model" to go back to the default, and the chosen model's effort levels ("auto" = the agent's setting); picking a model sets that model's own default effort (Codex reports it). In a running chat only that chat's agent's models are open (a conversation cannot move to another agent); a choice holds from the next turn on and for the chat until changed. The default a new chat starts with can be set on **Settings** (user menu, `#/settings`; kept per person on the server, `POST /ui/api/me/prefs` `{chat_default: {agent, id, effort} | null}`); without one it is the last one used. **Subagents** show as one folded block each in the log (task, running/done, its tool calls, its report) and never mix into the answer: Claude's `Agent`/`Task` tool call opens one, its own messages carry `parent_tool_use_id`, the tool_result ends it (the hand-back frame cut off); Codex's `collab_tool_call` (exec) / `collabAgentToolCall` (app-server) spawn and wait/close states; agy's `invoke_subagent` step (stream-json ACTIVE → DONE with `subagent_info`) or ACP tool call. Events carry `sub` (its id) and, on a `sub` event, `status`; the server keeps which run (`subs`, closed when the turn ends) and the board card says "N subagents". **Live chats (Claude Code):** the companion keeps one `claude -p --input-format stream-json` per chat running between turns (`LIVE` in chat.py, the pc reports `live: ["claude"]`). While it works, **Send** (Ctrl+Enter) hands the message to the companion at once (`mode: now`, `live` in the queue entry, out in `GET /machine/chats` as work with its mode) and it goes into the running process: Claude takes it into the turn it is in (measured: a message sent mid-step is answered in the same turn); **Queue** (Alt+Enter) waits in line for the next turn; **Force** (Ctrl+Shift+Enter, or the red button with an empty box and messages waiting) interrupts the step the native way (`control_request` interrupt; the process stays) and sends the message after it; **Stop** interrupts without a message. A background subagent goes on after the answer; when it ends the agent goes on by itself (events with `auto`: the chat runs again). A message written during a turn may start one more right after the result: the turn counts as over when nothing comes within 3 s. **A companion restart** (an update, a crash) does not end a live chat: each agent runs under a small host process of its own (`chat_host.py`, its own process group; on Windows out of the scheduled task's job), its output going straight to a file and its input fed from another (`companion/live/<chat>-<id>/`); the companion saves how far it read and the turn's state at every flush and every message written (`state.json`), and a new companion picks every running one up before its first poll (`chat.adopt`) and reads on from there, Codex's JSON-RPC and agy's ACP prompt included (tested end to end for all three: a turn started before the restart ends after it, in the same agent). A tool approval Claude asks while the companion restarts is asked again of the new one (up to 2 minutes). Another model, effort or YOLO setting restarts the process between turns (the conversation resumes); idle for 15 min with no subagent running, it ends and the next message resumes it. **Codex** is live too: one `codex app-server` per chat with one thread (`CodexLive`); Send while it works is `turn/steer` (measured on Codex 0.166: taken into the same turn), Force and Stop `turn/interrupt` (the turn ends "interrupted", the server stays), YOLO as thread settings (`approvalPolicy never`, `danger-full-access`), Default named once (`config/read`). **agy** (`AgyLive`): with YOLO one `agy --input-format stream-json`, without it one `agy acp`; agy runs a message sent during a turn as the next turn (measured on agy 1.4.12) and has no interrupt, so Send while it works goes right after, and Force and Stop end that agy; the conversation goes on in a new one (`--conversation` / `session/load`), for a Force with the message. **A subagent as a chat of its own** (in the list under its chat: only the running ones; the finished ones behind "+N finished subagents"; the server keeps a chat's newest 20; Claude Code's subagents start none of their own, a Codex subagent's own subagents show at the same level): the chat list shows each chat's subagents under it (`sub_list` in its meta: name, state, its agent id `aid` from Claude's `task_started` task_id or Codex's thread id); `#/chats/<chat>/sub/<id>` shows its own output only (its words, tool calls and report, from the chat's events with that `sub`), and a message there goes to the main agent, worded to pass it on (Claude: SendMessage to its agent id; Codex: send_input to its thread; agy: send_message to the subagent's own conversation, named in its DONE step's subagent_info; tested 2 Nov 2026: the subagent answered from its own memory). Subagents running now are pinned above the box (a click opens their block). **Tokens**: `usage` events, from Claude's `result.usage` (all tokens of the turn, cache reads included; the context = what the last main step sent) and its subagents' `task_progress`/`task_notification` `usage.total_tokens`, Codex's `turn.completed.usage` (exec: the thread's total so far, measured 25.6k then 76.7k after three turns, so it replaces) or `thread/tokenUsage/updated` (app-server, this thread's only), agy's `result.usage` (counted per turn; not verified across turns); subagent progress at most every 5 s; the server keeps the chat's `used` and `ctx` and each subagent's tokens (in its block); the chat head shows "35k context · 71k used". **Own branch**: a new chat with "Own branch" on (`worktree: true` in `POST /ui/api/chats`, carried in every work item) runs its agent in a git worktree of its own on branch `chat/<id>` (the workers' `worktree()`, under `companion/../worktrees/`), made at its first message and reused after; the chat says so once; a folder outside git runs in place. Merging and removing it is up to you (Archive leaves both). Its git pill and diff are the worktree's, never the folder's own checkout: the companion keeps which chats run in a worktree (`chat_worktrees.json`, the newest 50) and reports each one's pill against its base by chat id (`chats` in `POST /machine/report`), which the board shows for that chat; a diff request names the chat (`chat` in the `diffs` of `GET /machine/chats`) and the companion diffs its worktree, found the same way it was made (`workers.worktree(..., make=False)` only looks, never makes one). **Chats read each other**: MCP tools `knowledge_chats` (the chats on this token's pcs, and those of its owner's other tokens, newest first) and `knowledge_chat_read` (one conversation: owner and agent text, tool lines, no subagents, the newest 20k characters, marked as data, not instructions), so an agent can build on what another chat found. **Notifications**: Settings, "Tell me in this browser" (kept per browser, `kn_notify`) gives a desktop notification for each new Needs-you item (key + sig; the first three each, the rest as one "and N more"; the seen set kept per tab in sessionStorage) while the tab is out of view; the page then also refreshes the board every 30 s out of view; a click opens the chat or the item. Browsers that notify only from a service worker (Android) get none: phones use the Matrix messages (`needs_per_hour`). **Attachments**: the paperclip in the box, a paste (a screenshot) or a drop adds files (at most 5 of 10 MB per message) as chips; on Send each goes up as raw bytes (`POST /ui/api/chat/file?machine=`, `X-Filename`; kept per machine under `chats/<pc>/files/<id>/<name>`, swept after 30 days or past 200), and the message carries a mark `⟦file:<id>/<name>⟧`; the companion fetches it once (`GET /machine/chats/file`, only its own machine's) into `companion/files/<id>/` and replaces the mark by `[attached file: <path>]` (off the poll thread, one line per chat: a big file holds up only its own chat, and a later message or Force of that chat waits for it; Stop meanwhile drops it), so every agent opens it with its own file tools (images too); the page shows images inline and anything else only as a download (`nosniff`). An image the agent looks at shows in the chat too, under its tool line (Claude's `Read`, agy's `view_file`, Codex's `imageView` item; png/jpg/gif/webp up to 10 MB, the file on disk at an absolute path): the companion puts it up once per file version (`POST /machine/chats/file?chat=`, only for a chat of its own machine) and appends the mark to the tool line; a file attached in the web UI keeps its own mark. A click on an image in a chat opens the chat's images in a new tab (`/ui/images`, `images.js`): scroll or the arrow keys go through them, Ctrl+scroll, a pinch, a double-click or +/- zoom, drag pans, a thumbnail strip jumps, Esc or × closes the tab. The list reopens the chat last open when you come back (kept per browser, `kn_last_chat`; its × clears it; a phone starts on the list). In **Side by side** the cards' text keeps about the same size on screen while you zoom (14 px from 0.55× to 1.6×, `--bd-k`), and Archive there takes only that card off. **Archive** (chat head, or the row's ⋯ menu) takes a chat off the board and the list (it stays under the list's Archived filter; `POST /ui/api/chat/close {machine, id, closed}`), not while a turn runs; a new message opens it again. The chat list's width is dragged at its edge (arrow keys, double-click resets; kept per browser); the chat uses the whole width. A pc whose companion is older than 0.22 lists no models: its agents show as "<agent> (its own model)". The companion reports per agent what it offers (Claude Code's aliases fable/opus/sonnet/haiku, `codex debug models` with visibility list, `agy models` until an ACP session ran, then the list ACP itself offers, which both ways accept; asked in the background, again after 6 h, after 10 min when empty; no probe session, which would leave an empty agy conversation for `agy --continue`), the server refuses anything else, and the turn gets it as flags (`--model`/`--effort`, Codex `-m` and `-c model_reasoning_effort`) or, over JSON-RPC, in Codex's `turn/start` and agy's `session/set_model`. agy has no effort list: Gemini's model names carry the level and its other models refuse `--effort`. A model the agent refuses fails the turn with the agent's own message; the page sends a choice only when it was changed in that box (a saved model the pc no longer lists stays saved, not turned into Default unasked); messages waiting in line run with the chat's choice when their turn starts; Codex keeps a `turn/start` override for the thread, so Default is named there (`config/read`, else `model/list` isDefault); **Chats** lists them beside the open one (`#/chats/<pc>/<chat>`). The server only relays, pull only like the actions: the UI posts a message
  (`POST /ui/api/chat/send`), the pc's companion fetches it (`GET /machine/chats`, every ~2 s while a chat is active,
  else ~10 s), hands the message to the chat's running agent (see Live chats above; message on stdin, never on a
  command line), the first message a new conversation and a new process the agent's own continuation, and posts the
  output back in small batches (`POST /machine/chats/events`). With YOLO on for that agent there, it runs with the
  agent's own YOLO setting (`claude --dangerously-skip-permissions`, Codex `approvalPolicy never`, agy
  `--dangerously-skip-permissions`). Without YOLO it starts
  with the same narrow set a worker has (edits in the folder, the knowledge tools, `git status/add/commit`, Claude also fixed `git diff`/`git log` forms)
  and **asks you for anything else**, each agent its own native way: Claude through its permission prompt tool
  (`--permission-prompt-tool`, a small stdio MCP server of the plugin, `approval_mcp.py`, that asks the companion on
  127.0.0.1 with its local key), Codex over `codex app-server` (workspace-write sandbox, approval policy on-request,
  `thread/resume` continues the thread), agy over `agy acp` (`session/load` continues the conversation; agy's
  stream-json mode denies by itself). The turn pauses; the companion asks the server
  (`POST /machine/chats/ask`), and the chat card shows the request (tool, command or path, the agent's reason) with
  **Allow once**, **Allow for this chat** and **Deny**; each waiting approval is also an item under **Needs you** on
  the board, answered there or in the chat (`POST /ui/api/chat/approve`, only the machine's owner). The answer goes back
  with the companion's next poll (`answers` in `GET /machine/chats`) and the agent continues; denied, it is told so
  and goes on without. No answer within 30 minutes (admin page, Settings, `chat_approval_minutes`) counts as denied
  and the chat says so; a turn that ends or is stopped withdraws what still waits. The card shows the whole request (a long one folded,
  up to 4000 characters; longer can only be allowed once). "Allow for this chat" allows exactly the same call (the
  same full input, compared by hash) again for the rest of the chat without asking; `git push`, anything that names a
  path outside the chat's folder (relative, `~` and `$HOME` paths resolved), Codex's file changes outside the folder or
  without named paths, and Codex's requests for wider sandbox rights can only be allowed once. Codex is judged on the
  command it will run, never on its parsed summary of it; a Codex file change and fetching a URL are never allowed
  without asking. git's own files (`.git/`, `.gitattributes`, `.gitmodules`) are never written without asking, and
  only once (agy workers get a deny rule for them; Claude protects them itself); agy and Codex chats run no shell
  command, git included, without asking; and every git a chat turn or worker without YOLO starts runs with
  `core.fsmonitor=false` and `core.hooksPath=/dev/null` (`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_NOSYSTEM=1`), so a
  config an agent wrote cannot run with an allowed git command. On the board an approval whose request is longer than
  its one-line title can only be denied there (Allow is in its chat, where it shows whole); bidi control characters in
  an approval show as `<U+202E>`. The machine's token is checked against today's token rules on every question and answer. Every question and answer, with who answered, is in the companion's
  activity log and the server's audit log (`chat-ask`, `chat-approve`). Codex without YOLO still cannot commit in a
  chat unless you allow it: the folder is a main checkout, and Codex keeps its `.git` read-only (opening it would let
  a sandboxed run change git hooks and config). A chat turn says it is one (`KNOWLEDGE_CHAT`, header `X-Knowledge-Chat`): like a worker it
  hears no task lists or "start your tasks", takes no lease, task or notice, and agy is not asked to register. Only the machine's owner sees or posts (admins
  too only on their own machines); a chat needs its pc online and says so. One file per chat under the state
  directory (`chats/<machine>/`), at most 50 chats per machine (the oldest go) and 1 MB per chat (the oldest output
  goes). Every turn, stop and failure is in the companion's activity log; a failure also shows in the chat.
- **Workers in the chat view:** Follow on a worker opens its transcript as a chat card
  (`#/chats/worker/<project>/<ID>`), with Steer and Take over for its owner; a worker taken over continues as an
  ordinary chat in its worktree. How it works: [tasks.md](tasks.md#follow-steer-and-take-over-a-worker).
